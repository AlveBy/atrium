# Мониторинг: скорость и доступность

[English](monitoring.md) · [Русский](monitoring.ru.md)

`alveby/atrium-monitoring` меряет, как быстро сайт отвечает и отвечает ли вообще. Всё на своём сервере, без внешних сервисов. Модуль делает три вещи:

- **замеры сервера** по каждому запросу: время до первого байта, запросы к базе и их время, попадания в кеш и промахи, пиковая память, медленные запросы с их SQL;
- **Web Vitals посетителей** (LCP, INP, CLS, TTFB, FCP) из настоящих браузеров, скриптом меньше 2 КБ, без cookies и личных данных;
- **доступность**: главная каждого сайта и адреса, которые вы добавите, открываются раз в минуту; после нескольких отказов подряд открывается инцидент и уходят письмо и сообщение в Telegram.

Цифры — на экране **Состояние сайта → Скорость и доступность**, по дням, неделям или месяцам, как p50, p75 и p95, и в плитке на рабочем столе.

## Установка

```bash
composer require alveby/atrium-monitoring
php artisan atrium:module:install alveby/atrium-monitoring
```

Команда создаёт таблицы и включает модуль. До этого пакет ничего не делает: ни посредника, ни скрипта, ни проверок. Сброс буфера, проверки и чистка идут из планировщика Laravel, так что cron должен раз в минуту вызывать `php artisan schedule:run`.

Значения по умолчанию — в `config/atrium-monitoring.php` (`php artisan vendor:publish --tag=atrium-monitoring-config`). Настройки оповещений — в панели, **Модули → Мониторинг**.

Экран открыт каждой роли с правом **Смотреть отчёты о скорости и доступности** (`monitoring.view`). При установке его получают все роли, которым видны проверки доступности; суперадмину оно есть всегда.

## Что меряется

**На сервере** посредник в группе `web` пишет одну строку на запрос:

| Значение | Что это |
|---|---|
| Время до первого байта | от начала запроса до готового ответа |
| База | число запросов и их общее время |
| Кеш | попадания и промахи (из модуля кеша, если он стоит, см. [ниже](#для-других-пакетов)) |
| Память | пик памяти запроса |
| Ошибки | доля ответов с кодом 5xx |

Запросы группируются по **маршруту** (по имени, а если его нет — по шаблону вроде `/catalog/{slug}`), по **сайту** и по **языку**. Запрос к базе дольше 100 мс (`slow_query_ms`) сохраняется со своим SQL, где каждое значение заменено на `?`, так что в журнал не попадают ни почта, ни пароль, ни id; один и тот же запрос из разных мест — одна строка. На один запрос сохраняется не больше 20 медленных.

**В браузере** публичная тема получает скрипт. Он ждёт, пока страницу скроют, и один раз отправляет через `navigator.sendBeacon`:

| Метрика | Хорошо до | Плохо после |
|---|---|---|
| LCP, отрисовка крупнейшего элемента | 2,5 с | 4 с |
| INP, отклик на действие | 200 мс | 500 мс |
| CLS, сдвиг вёрстки | 0,1 | 0,25 |
| TTFB, время до первого байта | 800 мс | 1,8 с |
| FCP, первая отрисовка | 1,8 с | 3 с |

Это пороги Google, и, как у Google, они применяются к 75-му перцентилю. Вместе со страницей уходит тип устройства (телефон, планшет, компьютер — по ширине экрана) и тип связи, если браузер его знает (`4g`, `3g`…).

Другая тема подключает скрипт одним тегом в своём шаблоне:

```blade
<x-atrium-monitoring::rum />
```

## Экран

**Состояние сайта → Скорость и доступность** (`/admin/monitoring`) состоит из трёх частей.

- **Сервер**: сколько запросов измерено, время до первого байта (p50, p75, p95), доля ошибок сервера, попадания в кеш, запросов к базе на запрос и память на p95; графики времени до первого байта и времени базы; самые медленные маршруты и запросы. Маршрут открывает этот же экран с фильтром по нему; запрос — свою страницу с его временем по дням и маршрутами, где он выполняется.
- **Посетители**: пять Web Vitals на p75 с оценкой словами (Хорошо, Требует улучшения, Плохо), график каждой и самые медленные страницы по LCP. Страница открывает экран с фильтром по ней.
- **Доступность**: каждая проверка со статусом, долей времени в строю и последним ответом, и недавние инциденты.

Фильтры: период (30 дней по дням, 26 недель по неделям, 13 месяцев по месяцам), сайт, язык и устройство. Таблица страниц считает все устройства и языки, поэтому при этих фильтрах она скрыта.

Если стоит журнал ошибок (`alveby/atrium-errors`), у страницы в таблице самых медленных и у страницы на экране запроса есть ссылка на ошибки этого адреса (если администратору можно читать журнал). Группа «Состояние сайта» в боковом меню собирает отчёт, проверки доступности и инциденты рядом с журналом ошибок.

Числа пишутся так, как принято в языке панели: `2.91 s` по-английски, `2,91 с` по-русски.

Плитка рабочего стола **Скорость и доступность** показывает Web Vitals на p75 за 7 дней, доступность за 30 дней, что лежит прямо сейчас, и пять самых медленных маршрутов. Её видят только те, кому открыт экран.

## Доступность и оповещения

Каждую минуту (`atrium:monitoring:uptime`):

1. У каждого включённого сайта есть проверка его главной, по его домену и папке (`https://shop.example.com/`, `https://example.com/blog/`). Выключили сайт — выключается и проверка. Другие адреса добавляются в **Состояние сайта → Проверки доступности**.
2. Каждый включённый адрес открывается, по десять одновременно, с таймаутом 10 секунд. Ответ меньше 400 — в строю; 4xx, 5xx, таймаут или отказ в соединении — отказ.
3. Проверка проходит четыре состояния:

| Сейчас | Результат | Дальше | Что происходит |
|---|---|---|---|
| любое | в строю | В строю | открытый инцидент закрывается, оповещение «снова работает» |
| В строю / Не проверялась | отказ, меньше N подряд | Сбоит | пока ничего |
| Сбоит | N-й отказ подряд | Лежит | открывается инцидент, оповещение «не отвечает» |
| Лежит | отказ | Лежит | инцидент считает отказы, нового оповещения нет |

N — это **Отказов подряд до инцидента** в настройках (по умолчанию 3: три минуты без ответа).

Оповещения уходят:

- **письмом** на адреса из **Почта для оповещений** (через запятую или с новой строки). Письма идут через почту Laravel; если стоит почтовый модуль, он их перехватывает, со своими ящиками и историей.
- **в Telegram**: создайте бота у @BotFather, добавьте его в чат или канал и заполните **Токен бота Telegram** и **Чат Telegram** (`-1001234567890` или `@site_alerts`). Токен хранится в таблице настроек, а не в коде; `ATRIUM_MONITORING_TELEGRAM_TOKEN` и `ATRIUM_MONITORING_TELEGRAM_CHAT_ID` в `.env` главнее. Токен никогда не коммитьте.

Оповещение пишется на языке приложения. Неудачное оповещение пишется в лог, без токена, и проверки не останавливает.

## Приватность

- Ни cookies, ни локального хранилища, ни отпечатка браузера.
- IP-адрес нигде не хранится: он нужен только в памяти, чтобы пускать не больше 30 замеров в минуту с одного адреса.
- Адрес страницы хранится без строки запроса и `#фрагмента`, так что `?email=` или метка кампании в базу не попадают.
- Посетителей с **Do Not Track** или **Global Privacy Control** не меряют вовсе: скрипт им даже не выводится.
- `rum.sample_rate` меряет только часть просмотров (0.1 — каждый десятый).
- Медленные запросы хранятся со значениями, заменёнными на `?`.

Ничего из этого не требует баннера про cookies.

## Почему это дёшево

Измеренный запрос не трогает базу. Посредник дописывает одну короткую JSON-строку в файл в `storage/app/atrium-monitoring` — уже после того, как ответ отправлен. Раз в минуту `atrium:monitoring:flush` забирает файл переименованием, пишет сырые строки пачками и добавляет каждый запрос в гистограмму его дня, одной транзакцией под блокировкой. Если файл перевалил за 256 КБ раньше, сбрасывает тот запрос, который это заметил, или отдаёт сброс в очередь, если `buffer.queue` называет соединение очереди. `server.sample_rate` меряет только часть запросов.

`php artisan atrium:monitoring:benchmark` меряет, сколько добавляет посредник. Он гоняет один и тот же имитированный запрос (20 запросов к базе, два чтения кеша, через настоящий диспетчер событий) без посредника и с ним, раундами, с записью в настоящий файл, и показывает медианный раунд. Команда падает, если посредник добавляет 1 мс или больше. На PHP 8.4 в Docker (`php:8.4-apache`, Linux, без Xdebug):

| Запросов к базе на запрос | Добавляется на запрос |
|---|---|
| 20 | 0,14–0,20 мс |
| 0 | 0,04 мс |

Xdebug в любом режиме замедляет PHP в разы; мерьте без него.

## Перцентили

p50 — значение, быстрее которого была половина запросов (или просмотров); p75 — три из четырёх; p95 — все, кроме одного из двадцати. По p75 Google оценивает сайт; p95 показывает медленный хвост, который среднее прячет.

Каждый день хранится гистограммой по каждому значению с корзинами через 5% (логарифмическая шкала от 1 мкс), так что перцентиль из неё отличается от точного не больше чем примерно на 2,5%. Гистограммы складываются, поэтому неделя или месяц — это сумма их дней, и перцентили месяца — это перцентили всех его запросов, а не среднее дневных.

## Сколько хранится

| Данные | Сколько | Таблица |
|---|---|---|
| Сырые запросы, медленные запросы, просмотры, результаты проверок | 7 дней | `monitoring_requests`, `monitoring_queries`, `monitoring_vitals`, `monitoring_check_results` |
| Дневные гистограммы | 13 месяцев | `monitoring_daily` |
| SQL медленных запросов | пока живут их дневные строки | `monitoring_query_texts` |
| Закрытые инциденты | 13 месяцев | `monitoring_incidents` |

`atrium:monitoring:prune` удаляет остальное каждую ночь в 03:17, кусками по 5000 строк, чтобы большая таблица надолго не блокировалась. Оба срока — в `retention`.

## Команды

| Команда | |
|---|---|
| `atrium:monitoring:flush` | записать буфер в базу (каждую минуту) |
| `atrium:monitoring:uptime` | проверить все адреса (каждую минуту) |
| `atrium:monitoring:prune` | удалить старые данные (каждый день, 03:17) |
| `atrium:monitoring:benchmark --requests=2000 --queries=20 --rounds=5` | измерить цену посредника |

С `schedule` = `false` запускайте их по своему расписанию.

## Для других пакетов

**Счётчики кеша.** Если зарегистрирован фильтр `atrium.cache.stats`, модуль берёт попадания и промахи запроса из него, а не считает события кеша Laravel. Фильтр получает `['hits' => 0, 'misses' => 0]` и возвращает числа текущего запроса:

```php
Hook::filter('atrium.cache.stats', fn (array $stats): array => [
    'hits' => $this->hits,
    'misses' => $this->misses,
]);
```

Модуль читает его, когда запрос завершается. Если вернулся не массив — берутся события.

**Инциденты.** `atrium.monitoring.incident.opened` и `atrium.monitoring.incident.resolved` срабатывают с моделью `Incident` (с загруженной `check`) — для третьего канала вроде Slack или SMS:

```php
Hook::on('atrium.monitoring.incident.opened', function (Incident $incident): void {
    // $incident->check->url, $incident->started_at, $incident->last_error
});
```

## Контраст и графики без цвета

Каждый график рисует p50, p75 и p95, и их можно различить без цвета: у p50 кружки и сплошная линия, у p75 квадраты и пунктир, у p95 треугольники и точки, а в конце каждой линии подписано её имя. Под каждым графиком те же числа таблицей, а SVG несёт их в `<title>` и `<desc>` для экранных чтецов. Оценка написана словами; у статуса доступности есть название и знак (● в строю, ◐ сбоит, ○ лежит).

Цвета линий на фоне панели (контраст по WCAG 2; для текста минимум 4,5:1, для линий 3:1):

| Линия | Светлые темы | на белом | на самом тёмном светлом фоне (#f7f3ec) | Ночь | на #161d27 |
|---|---|---|---|---|---|
| p50 | #0B5FA5 | 6,57:1 | 5,94:1 | #6CB4F0 | 7,61:1 |
| p75 | #B34700 | 5,50:1 | 4,97:1 | #F5A05B | 8,12:1 |
| p95 | #374151 | 10,31:1 | 9,32:1 | #E5E7EB | 13,69:1 |

Тема «Высокий контраст» рисует все три чёрным (21:1) и различает их только значками и штрихами. Подписи осей — приглушённым цветом темы (7,56:1 на белом в «Графите», 7,13:1 на #161d27 в «Ночи»).
