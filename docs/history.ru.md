# История записей

[English](history.md) · [Русский](history.ru.md)

Каждый модуль панели хранит историю своих записей без единой строки собственного кода: кто создал, изменил или удалил запись, когда, откуда и какие поля из чего во что поменялись; версии каждой записи, чтобы сравнить две и вернуть старую; и корзина, из которой удалённая запись восстанавливается.

## Журнал изменений

**Журнал изменений** в меню (`/admin/activity`) показывает изменения всех модулей, новые сверху, по 50 на странице. В каждой записи сказано, что произошло (создано, изменено, удалено, восстановлено, удалено насовсем), с какой записью какого модуля, кто это сделал, откуда (в панели, через API, импортом, командой, по расписанию) и когда, и есть таблица изменённых полей: название поля из формы, что было и что стало. Старое значение зачёркнуто, новое нет, и столбцы называются **Было** и **Стало**, так что они различаются не только цветом. Пока запись существует, на неё ведёт ссылка.

Над списком журнал сужается по модулю, по администратору и по дням (**С** и **По**, оба дня включительно). Фильтры остаются в адресе: суженный журнал можно положить в закладки или отправить.

В форме каждой записи есть кнопка **История**: те же записи журнала, но только про неё.

## Что пишется и откуда

Все сохранения проходят через одно место, поэтому запись в журнале появляется, что бы ни внесло изменение:

| Откуда изменение | Источник в журнале | Кто |
|---|---|---|
| Форма записи в панели | в панели | вошедший администратор |
| `/api/v1` и инструменты MCP | через API | владелец токена |
| Импорт CSV или Excel | импортом | тот, кто запустил импорт |
| Кнопка модуля на записи, массовое действие | в панели / через API | тот, кто нажал, даже если оно выполняется в очереди |
| Консольная команда, своя задача очереди | командой | никто («Система») |

У новой записи перечислены все значения, которые она получила, включая значения по умолчанию из модели. У изменённой — только поля, которые отличаются: сохранение без изменений не оставляет записи, а пустой текст и отсутствие значения считаются одним и тем же. Переводы сравниваются по языкам, поля связей — по выбранным id, пользовательские поля и SEO — так, как их показывает форма. Поля формы только для чтения не сравниваются. Удалённая запись пишется со своим названием, чтобы было понятно, что это было.

Запись журнала пишется в той же транзакции базы, что и сама запись: неудачное сохранение не оставляет следа, а удачное никогда не теряет свою запись в журнале.

Собственная кнопка модуля (`RecordAction`, `BulkAction`) может менять записи как угодно; всё, что она сохраняет через Eloquent, пока работает, попадает в журнал поле за полем — относительно того, что было в базе.

## Версии

Каждое сохранение оставляет версию записи: что было в её форме после него. **История** записи показывает их над записями журнала, новые сверху, у каждой — когда сохранена, кем и откуда; первая — запись в том виде, в каком она сейчас. Первое сохранение записи, которая была до начала истории, оставляет и то, какой она была, — как **До начала истории**.

**Сравнить** показывает две версии поле за полем, так же как запись журнала показывает изменение; выбранные версии остаются в адресе. **Вернуть** у старой версии после подтверждения возвращает её значения. Сохранение идёт через форму модуля, как при импорте: та же проверка, те же хуки, запись в журнале и своя версия — то, что было в записи до этого, остаётся в истории, и возврат отменяется тем же способом. Версию, которую форма уже не принимает (поле стало обязательным, значение больше не разрешено), вернуть нельзя, и сообщение говорит почему.

У каждой записи хранятся 50 последних версий, более старые удаляются; число задаётся `ATRIUM_HISTORY_REVISIONS` (0 — не хранить). В версии нет паролей, ключей и токенов (см. ниже). Запись, удалённая насовсем, уносит свои версии с собой.

Для **Вернуть** нужно право изменять запись (`{module}.update`); смотреть и сравнивать версии можно с правом её смотреть. В API то же самое: `GET /api/v1/{module}/{id}/versions` перечисляет версии со значениями полей, `POST /api/v1/{module}/{id}/versions/{version}/restore` возвращает одну и отвечает записью или 422 с тем, что не прошло; в MCP — инструменты `list_versions` и `restore_version`.

У администраторов версий нет: возврат старой обходил бы проверки их формы (последний суперадминистратор, пароль).

## Корзина

Удалённая запись модуля с содержимым (страницы, новости, товары, сами сайты) уходит в корзину, а не исчезает: её больше нет в панели, на сайте, в поиске, в карте сайта, в API и MCP, но в своей таблице она остаётся со всем, что у неё есть: файлами, SEO, пользовательскими полями, связями, версиями, дочерними записями. Служебные модули (администраторы, языки, заявки форм, журналы, пользовательские поля и настройки SEO) удаляют сразу, как раньше. Так ведут себя и **Удалить** в списке, и массовое **Удалить**, и `DELETE /api/v1/{module}/{id}`, и инструмент MCP `delete_record`.

**Корзина** в меню (`/admin/trash`) показывает удалённое, новое сверху, по 50 на странице: запись, модуль, кто удалил и когда, с фильтром по модулю. **Восстановить** возвращает запись как была и открывает её форму; **Удалить насовсем** после подтверждения удаляет её вместе с файлами и версиями (журнал изменений сохраняет, что было). Оба действия попадают в журнал: **Восстановлено** и **Удалено насовсем**.

То, что пролежало в корзине 30 дней, планировщик каждую ночь удаляет насовсем (`atrium:trash:empty`; cron сайта запускает `php artisan schedule:run`). Число дней задаёт `ATRIUM_TRASH_DAYS`; 0 — хранить всё, пока не удалят вручную. Запись, которую модуль удалять отказывается (`beforeAdminDelete()` или обработчик `atrium.record.deleting`), остаётся.

Для восстановления нужно право `{module}.restore`, для удаления насовсем — `{module}.force_delete`: эти два права есть в редакторе ролей у каждого модуля с корзиной. Корзина показывает модули, которые администратор может смотреть, и, если сайтов несколько, записи сайта, с которым работает панель, и модулей, общих для всех сайтов. В API то же самое: `GET /api/v1/{module}/trash` перечисляет записи с `id`, `title`, `deleted_at` и `deleted_by`, `POST /api/v1/{module}/trash/{id}/restore` возвращает одну и отвечает записью, `DELETE /api/v1/{module}/trash/{id}` удаляет её насовсем; в MCP — `list_trash`, `restore_from_trash` и `delete_forever`.

Запись в корзине сохраняет свой код и адрес: новая запись не может их занять, пока старую не восстановят или не удалят насовсем.

## Пароли и другие секреты

Пароль, ключ или токен никогда не пишутся в журнал, даже в виде хеша. Когда такому полю дают новое значение, в журнале сказано, что поле изменено, — без значения. Поле считается секретным, если это:

- поле ввода пароля (`TextField::make('password')->password()`);
- атрибут, который модель скрывает (`$hidden`, как `password` и `remember_token` у администраторов);
- поле, в имени которого есть одно из слов `atrium.history.secrets` в любом регистре: по умолчанию `password`, `secret`, `token`, `api_key`, `private_key`.

Свои слова добавляются в `config/atrium.php`:

```php
'history' => [
    'enabled' => env('ATRIUM_HISTORY_ENABLED', true),
    'revisions' => env('ATRIUM_HISTORY_REVISIONS', 50),
    'secrets' => ['password', 'secret', 'token', 'api_key', 'private_key', 'passport'],
],
```

## Кто что видит

Журнал показывает записи только тех модулей, которые администратор может смотреть (`{module}.view`); фильтр по модулю перечисляет только их. Кнопке **История** у записи нужно то же право, что и её форме. Если сайтов несколько, в журнале видно то, что сделано на сайте, с которым сейчас работает панель, и в модулях, общих для всех сайтов; история записи другого сайта не находится.

## Как выключить

Для всего сайта: `ATRIUM_HISTORY_ENABLED=false` в `.env`. Ничего не пишется, журнал, его пункт меню и кнопки **История** пропадают. Записанное раньше остаётся в таблице `admin_activity`, версии — в `admin_revisions`. Только версии: `ATRIUM_HISTORY_REVISIONS=0`. Корзина от этого не зависит.

Для одного модуля — в его модели:

```php
public static function hasAdminHistory(): bool
{
    return false;
}
```

Записи модуля не попадают в журнал, и в его форме нет кнопки **История**. Чтобы журнал остался, а версий не было:

```php
public static function hasAdminRevisions(): bool
{
    return false;
}
```

Чтобы записи модуля удалялись сразу, без корзины:

```php
public static function usesAdminTrash(): bool
{
    return false;
}
```

## Авторам модулей

Для сохранения через форму, API, MCP или импорт ничего делать не нужно: запись в журнал пишет ядро. Модуль, который пишет записи по-своему, вне запроса панели, может сделать это явно:

```php
use Atrium\Admin\History\ActivityLog;

$log = app(ActivityLog::class);

// Всё сохранённое внутри попадёт в журнал поле за полем, как от кнопки модуля.
$log->watch(fn () => $order->update(['status' => 'paid']));

// Называет источник и администратора того, что пишется внутри.
$log->during(ActivityLog::SCHEDULE, null, fn () => $this->publishDue());

// Одна запись вручную.
$log->record($order, ActivityLog::UPDATED, ['status' => ['old' => 'new', 'new' => 'paid']]);
```

Запись в корзине прячет глобальный scope (`Atrium\Admin\Scopes\TrashScope`): запрос, снимающий все scope (`withoutGlobalScopes()`), видит и её, поэтому снимайте только нужный, например `withoutGlobalScope(SiteScope::class)`. `beforeAdminDelete()` и `atrium.record.deleting` срабатывают и когда запись уходит в корзину, и когда её удаляют насовсем; `eloquent.deleted` слышен, когда она уходит в корзину, а `eloquent.restored` и `eloquent.saved` — когда возвращается, так что кеши и индексы следуют за ней без своего кода.

`ActivityLog::changes($before, $after)` сравнивает два массива значений полей так же, как форма, и возвращает то, что принимает `record()`.
