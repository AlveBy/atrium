# Переезд с WordPress

[English](wordpress.md) · [Русский](wordpress.ru.md)

`alveby/atrium-wordpress` переносит содержимое сайта на WordPress в Atrium: записи становятся новостями, страницы — страницами, каждый другой тип записей получает свой модуль со своими произвольными полями, а следом переезжают рубрики, метки, авторы, файлы, SEO и переводы. Потом он доказывает, что ничего не потерялось, и пишет карту 301-редиректов со старых адресов на новые.

База WordPress только читается. Старый сайт работает, пока вы не переключите домен.

## Что нужно

- Установленный Atrium ([Установка](installation.ru.md)), лучше сначала у себя на компьютере: перенос можно повторять, а боевой сайт — потом.
- Модули «Новости» и «Страницы», если записи и страницы должны попасть туда: `php artisan atrium:module:install alveby/atrium-news` и `alveby/atrium-pages`. Без них записи и страницы получат свои модули, как любой другой тип записей.
- Копия базы WordPress (дамп из панели хостинга, `mysqldump` или `wp db export`), залитая в базу, до которой дотягивается ваш Atrium. Запускать сам WordPress не нужно.
- Копия папки `wp-content/uploads`.

```bash
composer require alveby/atrium-wordpress --dev
php artisan vendor:publish --tag=atrium-wordpress-config
```

## 1. Подключить базу WordPress

Добавьте в `config/database.php`, рядом с остальными, подключение `wordpress`:

```php
'wordpress' => [
    'driver' => 'mysql',
    'host' => env('WORDPRESS_DB_HOST', '127.0.0.1'),
    'port' => env('WORDPRESS_DB_PORT', '3306'),
    'database' => env('WORDPRESS_DB_DATABASE', 'wordpress'),
    'username' => env('WORDPRESS_DB_USERNAME', 'root'),
    'password' => env('WORDPRESS_DB_PASSWORD', ''),
    'charset' => 'utf8mb4',
    'collation' => 'utf8mb4_unicode_ci',
],
```

а значения — в `.env`. Если таблицы начинаются не с `wp_` (смотрите `$table_prefix` в старом `wp-config.php`), задайте `WORDPRESS_TABLE_PREFIX`. Каждая команда принимает и `--connection` с `--prefix`. Посмотрите, что там есть:

```bash
php artisan atrium:wordpress:analyze
```

Команда покажет языки, типы записей с числом записей, произвольными полями и тем, куда уходит каждый тип, таксономии, а ещё — что не переедет и почему. `--json` выдаёт то же для скрипта.

Куда уходит каждый тип, решается так, а меняется в `post_types` в `config/atrium-wordpress.php`:

- `post` уходит в «Новости», `page` — в «Страницы», если модуль установлен и у типа нет произвольных полей: в модулях для них нет места. Записи с произвольными полями получают вместо этого свой модуль. Отправить их в «Новости» или «Страницы» всё равно можно строкой `'post' => 'news'`, тогда поля попадут в отчёт как потерянные.
- Каждый другой публичный тип (рецепт, проект, товар какого-нибудь плагина) получает свой модуль: миграцию и модель с формой админки, как инфоблок Битрикса. Поля ACF сохраняют подписи, типы и порядок; остальные произвольные поля находятся по значениям.
- `'product' => 'skip'` оставляет тип на старом сайте; `'recipe' => ['table' => 'recipes', 'model' => 'Recipe', 'prefix' => 'recipes']` задаёт ему таблицу, модель и адрес.

## 2. Принести файлы

Скопируйте `wp-content/uploads` куда угодно на новый сервер и укажите эту папку в `WORDPRESS_UPLOADS_PATH`. Файлы ложатся в `public/wp-content/uploads`: адреса у них остаются прежними, так что старые ссылки и поиск по картинкам продолжают работать, а тексты ссылаются на них уже на новом сайте.

## 3. Перенести

```bash
php artisan atrium:wordpress:migrate
```

выполняет всю цепочку: модели и миграции для новых модулей, `migrate`, данные и проверку. Каждый шаг можно запустить и отдельно, в таком порядке:

```bash
php artisan atrium:wordpress:generate
php artisan migrate
php artisan atrium:wordpress:migrate:data
php artisan atrium:wordpress:parity
```

`generate` кладёт модели в `app/Models`, миграции — в `database/migrations` и печатает строки, которые нужно добавить в `config/atrium.php`: `resources` ставит модули в меню админки, `public_urls` открывает их записи на сайте.

```php
'resources' => [
    App\Models\Recipe::class,
    App\Models\Cuisine::class,
],
'public_urls' => [
    App\Models\Recipe::class => 'recipes',
],
```

Сгенерированные файлы задуманы для перегенерации, а не для правки: `generate` отказывается перезаписать файл, который писал не он, `--force` перезаписывает всё равно, а после перегенерации посмотрите `git diff app/Models`.

Что переезжает:

- Записи, страницы и произвольные типы записей: заголовок, текст (комментарии блоков Гутенберга убираются, переносы строк классического редактора становятся абзацами), анонс, ярлык, дата, порядок, родитель страницы, миниатюра записи. Опубликованные и запланированные записи активны; черновики, записи на утверждении и личные переезжают скрытыми; корзина, редакции и автосохранения остаются.
- Рубрики, метки и произвольные таксономии — с деревом, описаниями и привязкой к записям.
- Пользователи, которые что-то написали, — как авторы: имя, логин, почта. Пароли — никогда.
- Вложения: файлы — в `public/wp-content/uploads`, а в медиабиблиотеку (коллекция «WordPress») — с заголовком, alt-текстом, описанием и размерами, которые нарезал WordPress. Ссылки в текстах на загрузки старого домена ведут на новый сайт.
- ACF: текст, число, да/нет, даты, варианты выбора, картинки, файлы, галереи, ссылки, группы, повторители и гибкое содержимое.
- SEO из Yoast или Rank Math: заголовок и описание (с подставленными переменными `%%title%%` / `%title%`), ключевые слова, Open Graph, канонический адрес, noindex и nofollow — для записей и для терминов.
- Языки из WPML или Polylang: переводы записи становятся языками одной записи, а языки добавляются в Atrium, и основным становится основной язык WordPress. Сайт без языкового плагина попадает под язык из его `WPLANG` или под `language` из конфига.

Запускайте снова когда угодно: записи узнаются по ID из WordPress в таблице `wordpress_map`, и второй запуск обновляет их, а не удваивает.

## 4. Проверить

```bash
php artisan atrium:wordpress:parity
```

заново собирает по базе WordPress, что должно быть в каждой записи, и сравнивает с тем, что есть в Atrium: каждый язык, автор, термин и файл, поля каждой записи, родитель, рубрики и метки, SEO и редиректы. Пустой отчёт значит «ничего не потеряли»; если что-то расходится, команда завершается с кодом 1, и скрипт может на этом остановиться. `--format=markdown --output=parity.md` пишет отчёт в файл для заказчика, `--format=json` — для скрипта.

Предупреждения — не расхождения: в них то, чего не было и в самом WordPress (миниатюра, файла которой нет в `uploads`), и то, что перенесено сознательно без места (произвольные поля записей, отправленных в «Новости»). Заметки рассказывают, что пришлось починить по дороге, см. [Грязные данные](#грязные-данные).

Так проверяются данные. Открывается ли на новом сайте каждая страница старого, проверяется по живому старому сайту — с редиректами из следующего шага.

## 5. Перенаправить старые адреса

```bash
php artisan atrium:wordpress:redirects --format=nginx --output=wordpress-redirects.conf
```

пишет 301 с каждого старого адреса на новый: записи — по структуре постоянных ссылок сайта (`/%year%/%monthnum%/%postname%/`, `/%category%/%postname%/` и остальные, или простые `/?p=123`), короткие ссылки `/?p=123`, страницы — с ярлыками родителей, рубрики и метки — с префиксами рубрик и меток, каждый язык — со своей папкой или своим `?lang=`. `--format=apache` пишет строки `RewriteRule` для `.htaccess`, `--format=csv` — таблицу, чтобы прочитать или загрузить куда-то ещё.

Для nginx подключите файл в блоке `http`, а в `server` сайта перенаправляйте:

```nginx
if ($atrium_wordpress_redirect) {
    return 301 $atrium_wordpress_redirect;
}
```

## 6. Догнать и переключить

Пока вы собираете новый сайт, редакторы продолжают работать в WordPress. Перед переключением перенесите их правки со свежего дампа:

```bash
php artisan atrium:wordpress:sync --prune --audit
```

переносит только записи, изменённые с прошлого запуска, и новые, `--prune` удаляет те, что в WordPress удалили или отправили в корзину, а `--audit` в конце запускает `parity`.

Импортёр — зависимость для разработки, поэтому последний `sync` выполняется там, где вы делали перенос. Потом перенесите эту базу и `public/wp-content/uploads` на боевой сайт ([Установка](installation.ru.md)), добавьте редиректы в веб-сервер и направьте на него домен.

## Грязные данные

Настоящие базы WordPress старые, и импортёр к этому готов:

- Сериализованный PHP, сломанный поиском с заменой по базе (неверные длины строк в `wp_postmeta` и `wp_options`), чинится и читается; заметка говорит, где.
- Файл, который в базе есть, а в `uploads` нет, попадает в список, а запись переезжает без него.
- Две записи с одинаковым ярлыком получают `-2`, `-3`: страницы — в пределах родителя, остальные — в пределах языка.
- Тексты в другой кодировке или с битыми символами переводятся в UTF-8; ярлыки в процентной кодировке (кириллические) раскодируются.
- Страница, чей родитель пропал или другого типа, и петля из родителей уходят на верхний уровень — с заметкой.
- Автора уже нет в `wp_users`: запись переезжает без автора, с заметкой.

## Что пока не переносится

- **Выгрузка WXR**: импортёр читает базу. Файл выгрузки — в планах.
- **Комментарии, меню, виджеты и тема**: новый сайт рисует публичная тема (`alveby/atrium-theme`) по модулям или ваши собственные шаблоны Blade; меню собирается в Atrium заново.
- **Шорткоды и блоки плагинов** остаются в тексте как были; поищите `[` в текстах нового сайта.
- **Поля ACF «связь» и «объект записи»** хранят ID из WordPress.
- **SEO переводов**: значения Yoast и Rank Math берутся у записи на основном языке.
- **Адреса с отдельным доменом на язык**: редиректы покрывают папки и `?lang=`; для доменов пропишите их на каждом домене.
- **Страницы вложений, архивы авторов и дат**: редиректы для них не пишутся.
- **Сети мультисайта**: их сайты делят `wp_users`, а остальные таблицы несут номер сайта (`wp_2_posts`); импортёр ждёт один префикс на всё.
- **Пользователи, которые ничего не писали, роли, пароли, WooCommerce**: импортёр переносит содержимое. Магазин — в [планах](../ROADMAP.ru.md).
