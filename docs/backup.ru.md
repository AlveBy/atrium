# Резервные копии

[English](backup.md) · [Русский](backup.ru.md)

`alveby/atrium-backup` по расписанию копирует базы данных и файлы сайта в одно или несколько мест, хранит разумное число старых копий, пишет на почту, если что-то не так, и возвращает копию на место прямо из админки.

## Установка

```bash
composer require alveby/atrium-backup
php artisan atrium:module:install alveby/atrium-backup
```

Для расписания планировщик Laravel должен запускаться из cron раз в минуту:

```bash
* * * * * cd /path/to/site && php artisan schedule:run >> /dev/null 2>&1
```

На сервере должны быть программы для дампа: `mysqldump` для MySQL и MariaDB, `pg_dump` для PostgreSQL (версии не ниже серверной), `sqlite3` для SQLite. Для восстановления нужны `mysql`, `psql` и `sqlite3`.

Всё задаётся в `.env` или в `config/atrium-backup.php` после `php artisan vendor:publish --tag=atrium-backup-config`. Отдельный `config/backup.php` вести не нужно: модуль сам собирает настройки spatie из своих.

## Что попадает в архив

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `ATRIUM_BACKUP_DATABASES` | подключение по умолчанию | Подключения, которые нужно выгрузить, через запятую: `mysql,analytics` |
| `ATRIUM_BACKUP_DISKS` | `uploads` | Диски Laravel, файлы которых попадают в архив. `uploads` — диск, на который админка загружает файлы. Читаются только диски на этом сервере: у бакета свои копии |
| `ATRIUM_BACKUP_FOLDERS` | нет | Другие папки, абсолютным путём или от корня проекта: `public/upload` |
| `ATRIUM_BACKUP_PASSWORD` | нет | Шифрует архив (zip с AES-256). Без пароля архив не откроет никто, и админка тоже: храните его не на сервере |

Дампы согласованные: MySQL и MariaDB выгружаются с `--single-transaction`, если в настройках `dump` подключения не сказано иначе, а `pg_dump` и дамп SQLite делают снимок сами. Архивы — zip со сжатием уровня 6, после записи их проверяют.

## Куда уходят архивы

Каждое имя в `ATRIUM_BACKUP_DESTINATIONS` — это диск Laravel; архив копируется на все диски сразу, и одно недоступное место не мешает копированию в остальные. Модуль сам объявляет эти диски, если в `config/filesystems.php` нет диска с таким же именем:

| Диск | Что нужно | `.env` |
|---|---|---|
| `backups` | ничего: `storage/app/backups` на этом сервере | |
| `backup-s3` | `league/flysystem-aws-s3-v3` | `ATRIUM_BACKUP_S3_KEY`, `_SECRET`, `_REGION`, `_BUCKET`, `_ENDPOINT` (для S3-совместимого хранилища), `_PATH_STYLE`, `_ROOT` |
| `backup-ftp` | `league/flysystem-ftp` | `ATRIUM_BACKUP_FTP_HOST`, `_USERNAME`, `_PASSWORD`, `_PORT`, `_ROOT`, `_SSL` (по умолчанию включён) |
| `backup-sftp` | `league/flysystem-sftp-v3` | `ATRIUM_BACKUP_SFTP_HOST`, `_USERNAME`, `_PASSWORD` или `_PRIVATE_KEY` и `_PASSPHRASE`, `_PORT`, `_ROOT` |
| `backup-google` | `masbug/flysystem-google-drive-ext` | `ATRIUM_BACKUP_GOOGLE_CLIENT_ID`, `_CLIENT_SECRET`, `_REFRESH_TOKEN`, `_FOLDER` |
| `backup-dropbox` | `spatie/flysystem-dropbox` | `ATRIUM_BACKUP_DROPBOX_APP_KEY`, `_APP_SECRET`, `_REFRESH_TOKEN` (или короткоживущий `_TOKEN` для быстрой пробы), `_ROOT` |

Например, копия на сервере и ещё одна в бакете S3:

```bash
ATRIUM_BACKUP_DESTINATIONS=backups,backup-s3
ATRIUM_BACKUP_S3_BUCKET=site-backups
```

Адаптер для нужного диска ставится через Composer; пока его нет, этот диск сообщает об ошибке с названием пакета, а остальные работают. Аккаунты, ключи и токены принадлежат владельцу сайта: создайте их в консоли провайдера и впишите в `.env`.

Dropbox: `spatie/flysystem-dropbox` пока не ставится вместе с Guzzle 8, поэтому диск `backup-dropbox` ждёт его релиза, который это умеет. Google Drive: создайте в Google Cloud клиент OAuth типа «Desktop app», разрешите Drive API и один раз получите refresh-токен (например, в Google OAuth Playground); токены доступа модуль обновляет сам.

## Расписание и хранение

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `ATRIUM_BACKUP_FREQUENCY` | `daily` | `daily`, `weekly` или `off` |
| `ATRIUM_BACKUP_TIME` | `02:00` | Время суток в часовом поясе приложения |
| `ATRIUM_BACKUP_DAY` | `0` | Для weekly: 0 — воскресенье, 6 — суббота |
| `ATRIUM_BACKUP_KEEP_ALL_DAYS` | `2` | Столько дней хранится каждый архив |
| `ATRIUM_BACKUP_KEEP_DAILY` | `7` | Дальше по одному в день столько дней |
| `ATRIUM_BACKUP_KEEP_WEEKLY` | `4` | Дальше по одному в неделю столько недель |
| `ATRIUM_BACKUP_KEEP_MONTHLY` | `6` | Дальше по одному в месяц столько месяцев |
| `ATRIUM_BACKUP_KEEP_YEARLY` | `2` | Дальше по одному в год столько лет |
| `ATRIUM_BACKUP_MAX_MEGABYTES` | `5000` | Дальше уходят самые старые, пока архивы не займут не больше этого |

Самый новый архив не удаляется никогда. Старые архивы чистятся каждый день через час после времени копирования, проверка состояния идёт ещё через час.

## Проверки состояния и письма

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `ATRIUM_BACKUP_MAX_AGE_DAYS` | 1 для daily, 8 для weekly | Столько дней может быть самому новому архиву |
| `ATRIUM_BACKUP_SIZE_JUMP_PERCENT` | `50` | Самый новый архив вырос или уменьшился больше чем на столько по сравнению с предыдущим: половина сайта пропала или что-то раздулось. `0` выключает проверку |
| `ATRIUM_BACKUP_MAIL` | все суперадмины | Кому слать письма, через запятую |

Письмо уходит, когда копирование не удалось, когда хранилище недоступно, когда архив слишком старый или размер скачком изменился, и когда не удалась очистка. После успешных запусков писем нет.

## Экран в админке

Раздел **Резервные копии** есть в меню только у суперадминов: в архиве лежат хеши паролей всех администраторов и все заявки с форм, поэтому ни одной роли его дать нельзя. На экране:

- все архивы на всех хранилищах: размер, дата и место, а также ссылки, чтобы скачать, восстановить или удалить;
- кнопка **Создать копию**: всё сразу, только базы данных или только файлы;
- по каждому хранилищу: доступно ли оно, сколько в нём архивов, самый новый, занятое место и непройденные проверки;
- действующие настройки и журнал запусков, восстановлений, скачиваний и удалений с именем того, кто их сделал.

«Создать копию» и восстановление выполняются после того, как страница уже ответила, поэтому на большом сайте не упираются в лимит времени веб-сервера; страница показывает ход работы и обновляется, когда всё закончится. С `ATRIUM_BACKUP_QUEUE=redis` (или любым другим подключением очереди) они уходят в очередь на воркер. Одновременно идёт только одно копирование или восстановление.

## Восстановление

Восстановление заменяет данные. Пока ничего не изменилось, окно восстановления читает архив и показывает, что в нём лежит: каждую базу данных с типом базы, из которой она выгружена, размером дампа и базой, в которую она попадёт; каждую папку с числом файлов новых, изменённых, без изменений и тех, которых нет в архиве; и предупреждения (дамп из другого типа базы, подключения уже нет, дампа нет в архиве). Чтобы продолжить, введите имя файла архива.

Что делает восстановление и чем это грозит:

- Каждая база данных из архива очищается и заполняется заново из дампа. Всё, что записано после создания архива, пропадёт: заказы, заявки с форм, правки.
- Сессии администраторов и API-токены вернутся такими, какими были тогда: кого добавили позже, потеряет доступ, а отозванный позже токен снова заработает.
- Файлы из архива перезапишут файлы с теми же именами. Добавленные позже останутся, если не отмечено «Удалить файлы, которых нет в архиве».
- Пока восстановление идёт, на сайте могут быть ошибки или полувосстановленные данные. Если посетители не должны этого видеть, сначала включите режим обслуживания: `php artisan down`.
- Дамп восстанавливается только в базу того же типа: MySQL в MySQL, PostgreSQL в PostgreSQL.

Чтобы неудачное восстановление можно было отменить, сначала делается свежая копия текущего состояния (включено по умолчанию: «Сначала сохранить текущее состояние»). Если её сделать не удалось, восстановление не начинается.

Из командной строки то же самое со сводкой и вопросом, а с `--dry-run` — только сводка:

```bash
php artisan atrium:backup:restore --dry-run
php artisan atrium:backup:restore 2026-11-17-02-00-00.zip --disk=backups --only-db
```

## Команды

| Команда | Что делает |
|---|---|
| `atrium:backup:run` | Копия сейчас; `--only-db`, `--only-files` |
| `atrium:backup:restore {archive?}` | Восстановление, по умолчанию из самого нового архива; `--disk=`, `--only-db`, `--only-files`, `--delete-extra`, `--no-safety-backup`, `--password=`, `--dry-run`, `--force` |
| `backup:list`, `backup:monitor`, `backup:clean` | Собственные команды spatie тоже работают, с теми же настройками |

## Что добавлено к spatie/laravel-backup

[spatie/laravel-backup](https://spatie.be/docs/laravel-backup) выгружает, архивирует, шифрует, копирует, чистит и следит за состоянием. Atrium добавляет:

- настройки в одном месте, из `.env`, с уже объявленными дисками для хранилищ;
- восстановление, которого у spatie нет: сводка по архиву, подтверждение вводом имени, предварительная страховочная копия, MySQL, PostgreSQL и SQLite, зашифрованные архивы, архивы на удалённых дисках;
- экран в админке только для суперадминов, со скачиванием и журналом, кто что делал;
- запуск из админки после ответа или через очередь, по одному;
- расписание по частоте, времени и дню недели, без правки консольного ядра;
- проверку внезапного изменения размера и письма суперадминам по умолчанию;
- согласованные дампы MySQL по умолчанию и диски Google Drive и Dropbox с обновляемыми токенами.

## Тесты

Тесты пакета, как и остальные, идут на SQLite, MySQL и PostgreSQL. Хранилища проверяются на настоящих серверах, если их указать, и пропускаются, если нет:

```bash
ATRIUM_TEST_S3_ENDPOINT=http://127.0.0.1:9090 ATRIUM_TEST_SFTP=127.0.0.1:2222 ATRIUM_TEST_FTP=127.0.0.1:2121 vendor/bin/phpunit packages/backup/tests
```

Для теста S3 нужен бакет `backups` (`ATRIUM_TEST_S3_BUCKET`), для SFTP и FTP — пользователь `atrium` с паролем `atrium`; папка SFTP — `/backups`, а `ATRIUM_TEST_SFTP_ROOT` и `ATRIUM_TEST_FTP_ROOT` меняют папки.
