# Changelog

All notable changes are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added
- Backup module (`alveby/atrium-backup`, on spatie/laravel-backup): the databases (MySQL, MariaDB, PostgreSQL, SQLite) in a consistent dump and the chosen disks and folders in one zip, encrypted with `ATRIUM_BACKUP_PASSWORD`, copied to a local folder, S3 or S3-compatible storage, FTP, SFTP or Google Drive, daily or weekly, with daily/weekly/monthly/yearly retention and a size cap. An e-mail to superadmins when a backup or a destination fails, the newest archive is too old or its size jumps. A **Backups** screen for superadmins only: the archives on every destination, **Back up now**, download, delete, destination health, and a restore that first shows what the archive will change (dumps, target databases, new/changed/extra files, warnings), asks for the archive's name and makes a safety backup; the same from `atrium:backup:restore` with `--dry-run`. Runs after the response or on a queue, one at a time, logged with who did it. See [docs/backup.md](docs/backup.md).
- A CDN for files and images, off until `ATRIUM_CDN_URL` is set: uploads, files from 1C-Bitrix, pictures in texts, the Open Graph image, admin list thumbnails and, with `ATRIUM_CDN_ASSETS`, the Vite builds. Local files get `?v=` versions; deleting a file in the file manager purges it from Cloudflare or BunnyCDN, and `atrium:cdn:purge` does it by hand. With `ATRIUM_CDN_IMAGES` (cloudflare, bunny, signed imgproxy or a URL template) the theme asks for pictures at the width shown, with `srcset` and WebP/AVIF. `MediaUrl::to()` and `Cdn::srcset()` for your own views. See [docs/cdn.md](docs/cdn.md).
- `ATRIUM_UPLOADS_DISK`: the admin uploads to any Laravel disk, S3 included; a file on a remote disk is stored as its address on that disk's `url` (the CDN in front of the bucket).
- `atrium.superadmin_routes`: route-name prefixes that only superadmins may open, whatever their roles; a module adds its own (the backup module adds `admin.backups.`).
- "Made by AlveSoft Solutions" with the AlveSoft logo at the bottom of the admin's sidebar and under the sign-in form, linking to alve.by/en in a new tab, in the admin's language, with the white logo on a dark background; `ATRIUM_CREDIT=false` (`atrium.credit`) hides it.
- Captcha for the public forms of every module (`Atrium\Admin\Captcha`): `<x-atrium::captcha />` in the form and `app(CaptchaManager::class)->rules()` in the validation, chosen with `ATRIUM_CAPTCHA`. `image` is built in and needs no keys: a sum drawn as a noisy picture, the question encrypted in the form, answered once and expiring; `recaptcha` is Google reCAPTCHA v2 (`RECAPTCHA_SITE_KEY`, `RECAPTCHA_SECRET_KEY`; without keys the built-in one is used); others come with `extend()`. The reviews form asks it (`atrium-reviews.captcha`).
- Error pages in the theme: 403, 404, 419, 429, 500 and 503, and a general 4xx and 5xx page, in the site's design, brand and language; 404 links home and has a search box when the site has a search. A page of the app's own wins the Laravel way, and a site of several may have its own: `resources/views/errors/{site code}/404.blade.php`, then `resources/views/errors/404.blade.php` (or `4xx`/`5xx`), then the theme's, then Laravel's, with no change to `bootstrap/app.php`. `php artisan vendor:publish --tag=atrium-errors` copies the theme's pages into the app as a start. Server errors are drawn without the layout and the database; JSON and API requests keep JSON errors, the admin keeps its pages, and `php artisan down --render="errors::503"` prerenders the theme's 503.
- `php artisan atrium:make-package acme/atrium-reviews`: a module package to publish, made from the template in `packages/admin/stubs/module`: the manifest, a translatable model with its admin form and list, a migration, a demo seeder, labels, Testbench tests that pass as generated, a GitHub Actions workflow, a README and an MIT licence. `--model`, `--namespace`, `--title` and `--path` change the defaults.
- The Modules screen for a superadmin: **Switch off** / **Switch on** for every installed module (`atrium.disabled_modules`; data and settings stay, everything else treats it as not installed, submodules follow their parent, switching on runs the migrations it missed; hooks `atrium.module.enabled` / `atrium.module.disabled`), the packages Composer has that are not installed with the command for each, and a catalogue of the modules on Packagist (type or keyword `atrium-module`, alveby's first) with what each is here and how to add it.
- Ready-made sites (`alveby/atrium-solutions`): `php artisan atrium:solution:install law` turns a fresh project into a whole site: the modules it needs on and the others off (their data kept), the migrations, its content languages, the brand as the site name, its names for the modules in the admin and on the site, their addresses and the site menu, and its content in all 15 languages, set in the installer's country (`--locale=de` gives a Berlin firm with prices in euros, an Impressum and a Datenschutzerklärung; an unknown locale the American one); a second run doubles nothing. `atrium:solution:list` lists the solutions and the modules each still lacks; `--json` is the catalogue (texts in every language, modules, palette, fonts, screenshots, pages, install command). A solution is a folder with a `solution.json` and a seeder extending `SolutionSeeder`; other packages add their folders to `atrium-solutions.paths`. The first one is `law`, a made-up law firm with six practice areas, six lawyers in two departments, insights, two offices, a consultation form, a fees FAQ and client reviews.
- Team module (`alveby/atrium-team`, `atrium:module:install alveby/atrium-team`): people in departments with a photo, a position, a short description, a biography, email and phone, in every content language and per site. The theme draws `/team`, grouped by department, and a page per person; `--demo` adds two departments and three people in three languages. Admin labels in 15 languages.
- Submodules: a module lists its submodules in the manifest (`submodules`), or a submodule names its parent (`parent`); each is a package of its own. Installing a module installs the submodules Composer has, a submodule needs its parent installed, removing a module removes its submodules first, and the Modules screen lists them under it.
- The admin has a logo of its own, an arch with the name set in Space Grotesk (bundled, nothing is loaded from Google), in the sidebar, on the sign-in pages and as the favicon; `ATRIUM_LOGO` and `ATRIUM_FAVICON` still replace it. Five colour themes (graphite, day, night, sand, contrast) that each administrator picks in the menu under their name, or "As the system"; the default is `ATRIUM_ADMIN_THEME`. Every theme passes WCAG AA, checked by a test, and the selected menu entry and the active/hidden badges differ by shape as well as colour.
- A module package declares its own permissions in the manifest (`extra.atrium.permissions`: `"refund": "label"` or `"orders.export": {"label": ..., "with": "orders.view"}`). While it is installed they are checkboxes in their section's row of the role form, with their labels; on install, roles that have the `with` permission get them; `atrium:module:remove` takes them out of the roles.
- Hooks: actions and filters by name, for modules to meet without calling each other. `Hook::fire('atrium.order.paid', $order)` / `Hook::on(...)` (Laravel events, queued listeners work), `Hook::apply('atrium.search.sources', $sources)` / `Hook::filter(..., $priority)`; a hook nobody listens to costs one array lookup. The core fires `atrium.record.data`, `atrium.record.saved` and `atrium.record.deleted` when the panel or the API saves or deletes a record, `atrium.admin.menu` for the panel's menu, and `atrium.module.installed` / `atrium.module.removed`.
- The theme's footer says "Made with Atrium" (a link to the repository, in 15 languages) and every page has `<meta name="generator" content="Atrium">`. On by default; `ATRIUM_THEME_CREDIT=false` hides the link. The README asks, without making it a condition, to keep it.
- Every source file starts with the Atrium copyright header. Pint adds it to PHP (`header_comment` in pint.json), `php scripts/copyright-header.php --fix` to Blade, Vue, JS, CSS, shell and YAML, and `tests/Unit/CopyrightHeaderTest.php` fails without it.
- Docs module (`alveby/atrium-docs`): documentation pages made from the Markdown of a repository, the README, `docs/`, the changelog and every package's README, at `/docs/{version}/{page}` and `/{lang}/docs/…`. A sidebar, a contents list, GitHub's heading anchors, code coloured on the server by Phiki with light and dark themes at 4.5:1 or more, search in the language of the page with suggestions as you type, "Edit this page on GitHub". A page without a translation is shown in English with a notice, its canonical pointing to the English page and its hreflang listing only real translations. `atrium:docs:pull v0.2.0` copies a release out of git as one more version; the newest release is the default and older ones say so. Interface in 15 languages.
- Module settings: a module names a `settings` class in its manifest (`extra.atrium.settings`), extending `Atrium\Admin\Modules\ModuleSettings`, with fields of the admin's own types, their rules and defaults, for all sites or for each (`$perSite`). The panel gets a **Modules** screen listing the installed modules and a settings screen for each; the `{key}.settings` permission is in the module's row of the role form. Values are read with `Setting::get('shop.currency')` (the current site's value, else the field's default) and kept in `admin_module_settings`. The manifest may set the module's `key` and `title`. The catalog has the first one: products on a page of a section, per site.
- AI module (`alveby/atrium-ai`, on the Laravel AI SDK): a **Generate** link under text fields marked `->ai()` writes a description, a preview, the SEO title, description and keywords, or a picture's alt text, and **Translate** fills a translatable field's other languages. The text is offered in a dialog to edit or drop; nothing is saved until the editor saves. The SEO fields of `HasAdminSeo` have it already. Providers come in chains per kind of work (text, vision, embeddings) with fallback on a limit or a timeout; the defaults are free tiers (Gemini, Groq, OpenRouter) or a local Ollama, keys only from `.env`, and no key means no buttons. The provider is called after the response or by a queue worker, so the form never waits; prompts are Blade views; `ai_usage` logs task, provider, tokens and time without the texts; `atrium:ai:status` shows the chains and the usage. The same over `POST /api/v1/ai/generate` and the `generate_text` MCP tool. A module adds its own MCP tools through `atrium.mcp.tools`.
- `DisplayField`: read-only HTML on the edit form, drawn from the record by the server (`->html(fn (Model $record): string => …)`), for order lines, summaries and links. It is not on the create form and nothing is taken from the request for it.
- Buttons on a record that open the create form filled from it: `CreateFromRecord::make('subpage')->label('Subpage')->fill(['parent_id' => 'id'])` in `getAdministrationActions()` shows one in the list row and on the form. Pages use it for "Subpage".
- Modules as packages. A Composer package of type `atrium-module` describes what it brings in `extra.atrium` (`resources`, `public_urls`, `migrations`, `demo`). `php artisan atrium:module:install vendor/name` runs its migrations and lists it in `atrium.modules` (config/atrium.php): its models enter the menu, the role form, the API and MCP. `atrium:module:remove` asks whether to keep the data, drops the tables if not and takes the module out of the roles. A required module that is not installed stays out of the panel. Neither command runs Composer.
- Soft links between modules: `Atrium\Admin\Modules\Soft::when(Brand::class, fn () => [...])` puts fields, columns or tabs into a form or a list only when the other module is installed; `Atrium\Admin\Traits\HasSoftRelations` gives `softBelongsTo()`, `softBelongsToMany()`, `softHasMany()` and `softMorphTo()`, relations that find nothing (and query no missing table) without it. `Soft::targets()` lists the modules a review or a comment can be attached to.
- A list column may show an attribute of a related record: `TextColumn::make('brand.name')`.
- The demo shop is four module packages now: `alveby/atrium-catalog` (products and catalog sections), `alveby/atrium-brands`, `alveby/atrium-stores` and `alveby/atrium-news`. Each one installs and works on its own. A product links to its brand and to the stores that sell it softly: without those modules the fields are not in the form and the product page leaves them out. A module's demo seeder can extend `Atrium\Admin\Modules\DemoSeeder`. Admin labels in 15 languages.
- Pages module (`alveby/atrium-pages`): static pages in a tree with sort order, per site, the name and the text in every content language, an SEO tab and three templates (a page, a page with cards of its subpages, a full-width landing; more in `config/atrium-pages.php`). A page opens at the path of its codes from the root of the site (`/about/team`, `/de/about/team`) inside the theme's layout, with breadcrumbs and `hreflang`; a hidden page hides its branch; visible pages go into `sitemap.xml`. The route is a fallback, so the app's, the admin's and the theme's routes are matched first. `atrium:pages:import-bitrix` moves the static pages of a 1C-Bitrix site (`.php` files outside iblocks) from a copy of its files at their old addresses, with titles, texts and SEO properties; windows-1251 is converted, components are reported, a second run updates; the old `.php` addresses redirect to the pages. Installed with `atrium:module:install alveby/atrium-pages` (its `extra.atrium` manifest lists the model, the addresses and the migrations); `--demo` adds a shop's pages in three languages. Admin labels in 15 languages.
- FAQ module (`alveby/atrium-faq`, `atrium:module:install alveby/atrium-faq`): questions and answers in categories, with sort order, in every content language and per site; the answer is a `ContentField`. The theme draws `/faq` (every category) and `/faq/{code}` (one category) with FAQPage structured data (schema.org JSON-LD) in `<head>`; `<x-atrium-faq::questions category="delivery" />` puts a category's questions, with their structured data, on any page. With `--demo` it is filled with three categories of a shop's questions (delivery, payment, warranty) in English, German and Russian. Admin labels in 15 languages.
- The theme lets a module draw its pages with a view of its own: a model in `public_urls` names it in `themeView('index'|'section'|'page')`, and the theme keeps the routes, menu, languages and sitemap. The layout has `@stack('head')` for tags such as structured data.
- Reviews module (`alveby/atrium-reviews`): reviews with a 1–5 rating, the author's name, text and date, per site, moderated in the admin (new → published or rejected). Installed with `atrium:module:install alveby/atrium-reviews` (the first module with an `extra.atrium` manifest; the skeleton lists it in `atrium.modules`). A review is about the site or about a record of any module listed in `atrium-reviews.models` (`Product::class => 'Product'`); the link is a soft `morphTo` (`reviewable`) with no foreign key and no Composer dependency, so a removed module leaves its reviews in place, marked as removed in the admin. The public page `/reviews` and the form under the theme's record pages (or `<x-atrium-reviews::reviews :for="$record" />` anywhere) show the average rating and count with schema.org `AggregateRating`; the form has a honeypot and a rate limit per address. The numbers come from `review_counters` (count, rating sum and each rating per record and site), counted again from `reviews` after every change of a review is committed, with the counter row locked, so simultaneous reviews are all counted; `Reviews::summaries()` gives a whole list in one query and `atrium:reviews:recount` rebuilds the counters after an import.
- The theme draws the views listed in `atrium-theme.record_views` under every record page, so a module package can add its part there.
- Forms and submissions (`alveby/atrium-forms`): forms per site built in the admin (fields with a type, a label and options per content language, a required flag), `<x-atrium-forms::form code="…" />` on a page, submissions kept in the admin and mailed to the addresses set on the form; each form keeps its number of submissions (`submissions_count`) for the list. The forms ask the site's captcha (`ATRIUM_CAPTCHA`) when one is on; `atrium-forms.captcha` set to `false` keeps it off them. Installed with `atrium:module:install alveby/atrium-forms`; the demo app has it installed. Spam is stopped by a honeypot and a signed time check, with no outside service; one IP address may send a form 5 times a minute. Submissions keep the labels as they were, so they read the same after the form changes or goes.
- A module may switch off creating or editing its records in the admin: `isCreatableInAdmin()` and `isEditableInAdmin()` on the model return `false` for records that come from elsewhere, such as form submissions. The buttons go, and the routes and the API answer 403.

- MCP server at `/mcp` (laravel/mcp): an AI assistant (Claude, ChatGPT, Cursor) connects with an API token and gets seven tools — `list_modules`, `describe_module`, `list_records`, `get_record`, `create_record`, `update_record`, `delete_record`. Every call goes through the API itself, so validation, the current site, translations and the rights of the token and of its owner are the same; a refusal comes back as text the assistant can read. Off with `ATRIUM_MCP_ENABLED=false`, the path is `atrium.mcp.path`. Connect, for example, with `claude mcp add --transport http atrium https://example.com/mcp --header "Authorization: Bearer <token>"`.

Each admin picks one in the header (it is kept on the account); guests get their browser's language. English and Russian are written by hand, the rest are machine translations awaiting native review.

The form gets a language switch with error counts per language; only the default language is required, the others fall back to it. Unique rules (such as a page code) apply within one language. The list shows the default language and searches all of them; the API takes either a plain value (default language) or an object keyed by language code, and documents it.

A request gets its site by domain (an unknown or inactive domain gets the default site), the admin by the switcher in the header, the API by `?site=code`.
- Sites in folders, like `DIR` in 1C-Bitrix: a site may live under a path on a shared domain (`example.com/site2/`), set in the Sites module. A request gets the site of the longest matching folder on its domain (`/site2` never matches `/site22`), otherwise the domain's root site or the default site; a site with a folder and no domains opens in that folder on every domain. The language prefix follows the folder (`/site2/de/…`). Every public address carries the folder: record links, canonical, `hreflang`, pagination, `sitemap.xml` entries and old-slug redirects. - `use Atrium\Admin\Traits\BelongsToSite` (plus a `site_id` column) makes a module per-site: lists, forms, search and public pages see the current site's records only, new records get its id, unique rules apply within the site. Modules without it are shared by all sites.

Past 50 000 addresses it becomes an index of `sitemap-N.xml` parts. Cached, rebuilt when a record, a site or a language changes.
- `robots.txt` of every site, edited in the admin; empty means "allow everything", and a `Sitemap:` line is added when missing. Off production it always says `Disallow: /`. `atrium.robots = false` leaves it to `public/robots.txt`; while it is on, `atrium:install` removes Laravel's stock file and the admin warns about any other.

- Roles and permissions for administrators. A role is a named set of permissions, `{module}.{view|create|update|delete}` for every module (the panel's own sites, languages and administrators included) plus `api-tokens.use`; an administrator may hold several roles, and they add up. The menu, the dashboard gadgets, the list and form buttons follow the roles; a record the role may view but not edit opens read-only; anything else answers 403. Superadmins need no role, and only they manage roles, make other superadmins and touch a superadmin's account; the last active superadmin cannot be demoted, switched off or deleted. The permission to manage administrators is a high-trust one: whoever has it can reset another administrator's password.
- API tokens follow their owner: a token is issued for no more than its owner may do, and every request also checks the owner's permissions today, so taking a role away takes it away from the owner's tokens too. Administrators see and revoke their own tokens; a superadmin sees everyone's.
- `atrium:user --superadmin` makes a superadmin, or promotes an existing administrator when given their e-mail (a way back in when nobody is left to manage roles). The first administrator is always a superadmin. Upgrading makes every existing administrator a superadmin, so nobody loses access.
- Issue and pull request templates, Dependabot, and a `release` workflow: pushing a `v*` tag publishes a GitHub release with that version's notes from this file.

### Changed
- `atrium:install --demo` installs every module package Composer has (as `atrium:module:install` does) and fills each with its demo content, the modules a module suggests first. `ATRIUM_DEMO` and `atrium.demo` are gone, and so is `packages/admin/src/Demo`. The demo's tables and admin addresses lost the `demo_` prefix (`/admin/catalog_products`, `/admin/brands`). A site that installed the old demo keeps its `demo_*` tables: drop them by hand and run `atrium:install --demo` again.
- The dashboard's speed and performance tiles were copies of the 1C-Bitrix gadgets (green gradient cards, coloured bands, a glossy button). They are plain admin cards now: the site speed is a grey scale filled up to the median with the band named in words, the details button is an ordinary one.
- The demo article's page is drawn by the theme; the app's own article controller, its view and Laravel's welcome page are gone.
