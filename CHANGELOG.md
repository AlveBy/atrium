# Changelog

All notable changes are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added
- The `atrium` skin (`ATRIUM_THEME_SKIN=atrium`, the public demo's default): an indigo and amber design in Unbounded and Inter that draws the inner pages as well as the home page, light and dark, from a phone to a wide screen, in all 15 languages. Home: a hero with newest products as tiles, brands, sections as a bento grid, products, news, stores, the team, reviews, questions and a contact form, each left out when its module is not installed. Catalog: filters by brand and stock and a price sort in about 40 lines of JavaScript, working without it as a plain list. Product: a gallery, badge, price, a stock mark that is a tick and words, colours, features, the stores that have it, details, specifications, downloads and related products. Stores: facts and an OpenStreetMap map loaded only when the visitor asks for it. A skin may have the views `list` and `page` to draw the theme's lists and records, and `RecordView::blocks()` tells each property's field name (`code`). Contrast measured and checked in `SkinsContrastTest`; no colour carries meaning alone. See [docs/skins.md](docs/skins.md).
- Buttons on a record and bulk actions. A module, or another module through the `atrium.module.actions` hook, puts buttons on a record, in its list row and on its form: a link (another site included, optionally in a new tab), a server action (`RecordAction::handle()` returning a success or error message or a redirect, with an optional confirmation) and the existing `CreateFromRecord`. A list with bulk actions gets checkboxes and "select all on this page"; checked rows bring up a bar with their number and the buttons: **Delete** for those who may delete, and the module's own `BulkAction`s and those of other modules (`atrium.module.bulk_actions`). A bulk action gets only the checked records the administrator may see in the current site, at most 1000, and goes to the queue when it implements `ShouldQueue`. Each button has its own permission or uses `view`/`update`/`delete`: without it the button is not shown and the server answers 403; a switched-off module takes its buttons with it. The API lists and runs the server actions (`/api/v1/{module}/actions`, `/{id}/actions/{name}`, `/bulk/{name}`) with the token's and the owner's rights, and MCP has `list_actions`, `run_record_action` and `run_bulk_action`. Pages get bulk **Show** and **Hide**; the menus module adds **Add to header menu** to every record with a page on the site. Labels in 15 languages; the bar, the checkboxes and the confirmation work from the keyboard, the confirmation window keeps focus inside and closes with Escape, and success and error messages differ by icon and by the word read out, not only by colour.
- Import and export of CSV and Excel (xlsx) for every module of the admin ([docs/import-export.md](docs/import-export.md)): **Import** and **Export CSV** / **Export Excel** above each module's list, built from the module's own fields, custom fields and content languages. Import: upload a file and the first rows show which field each column fills, guessed from the column names in any of the 15 languages, the fields' keys and a module's synonyms, or taken from the last import of the same columns; records are found again by id, code or what the module offers, create and update, create only or update only; tree fields (a section, a parent) by name or path; pictures and galleries by URL, downloaded once into the media library (only from public addresses, redirects checked, JPEG/PNG/GIF/WebP by content, size and time limits), or by a path on the site. **Check** runs every row through the form's validation without writing and reports what will be created, updated and skipped and which rows fail and why; the import gives the same report. Every row is saved as the form saves it; an empty cell leaves the field as it is. UTF-8 and windows-1251, `;`, `,` or tab recognised by themselves. Large files are read in chunks from where the last step stopped, moved by a queue worker, by the scheduler every minute or by the progress page. Export: the list as it is on the screen, with its search, filters and sort, every matching record and not one page; the file goes back into the import with no edits, finding each record by its id; cells that a spreadsheet would run as formulas are written as text. `atrium:import {module} {file or URL}` (with `--like`, `--map`, `--key`, `--mode`, `--option`, `--check` and an exit code of 1 when a row fails, for a scheduled price list) and `atrium:export {module} {file?}`. Permissions of their own, `{module}.import` and `{module}.export`, in the role form. A model opts out with `isImportableInAdmin()` / `isExportableInAdmin()`, names the columns that find a record again with `getImportKeys()`, and adds columns, synonyms and settings through the `atrium.import.targets` and `atrium.import.options` hooks. Labels in 15 languages. xlsx is read and written with openspout/openspout.
- Catalog: products take part through those hooks (`Atrium\Catalog\ProductImport`): the article number, code and a new **External ID** field find a product again, `SKU`, `Артикул` and `Цена` are understood, the section is found by name or path and the missing ones are created when asked.
- AI in a public demo: while `ATRIUM_DEMO=true`, the AI module gives the whole site `ATRIUM_AI_DEMO_DAILY_LIMIT` provider calls a day (40 by default, `0` for no cap; a text or a helper question is one call, a translation one per language), shared by the **Generate** dialog, the helper, `POST /api/v1/ai/generate` and the MCP tool `generate_text`, so one visitor cannot use up the provider's free quota. At the limit the dialog says that the day's limit is used up and the API and MCP answer 429 with a `Retry-After`, and no provider is asked. The count is kept in the cache store `ATRIUM_AI_DEMO_STORE` (`file` by default), since the demo's hourly reset empties the database and the usage log with it. The dialog and the helper tell visitors that the demo is public and personal data must not be typed in. Nothing is counted or shown outside demo mode. Labels in 15 languages.
- AI provider chains skip what cannot answer. An entry that answers 403, or 400 "User location is not supported for the API use" (Gemini and Groq from a server in a country they refuse), is skipped for an hour (`atrium-ai.refused_for`) and the next entry answers, for the buttons, the helper, the API, MCP and embeddings alike. A provider may be listed with several models in a chain (`openrouter:model-a:free,openrouter:model-b:free`) and the next model is asked when the first is limited, overloaded or refuses; before, the second model of a provider was silently dropped from the chain.
- A web root that is not called `public`, for shared hostings that serve a fixed `public_html` or `www` ([docs/installation.md](docs/installation.md#when-the-document-root-is-fixed-public_html-www)): rename `public` and nothing else needs setting. A request takes its folder from `index.php`; artisan, before `.env` is read, takes `public` while it has its `index.php`, otherwise the only folder of the project whose `index.php` starts the app (`Atrium\Admin\Support\PublicFolder`), so `storage:link`, the published admin and theme assets and `atrium:install` land where the web server looks; `npm run build` finds the same folder. `atrium:install` and the robots.txt hint of the Sites module name the file in the folder it is in (`public_html/robots.txt`), not always in `public/`.

### Fixed
- Russian text was cut in the middle of the letter «х»: lines were split with a byte-wise `\R`, which takes the second byte of «х» (D1 85) for a line break. The docs menu showed «В�» for «Вход через соцсети» and «Дву�» for «Двухфакторный вход», the AI helper got the same cut headings of the guides, a form option with «х» fell apart into two, and a JavaScript error whose function name had «х» lost that frame. Lines now break only at `\r\n`, `\r` and `\n`.
- SEO: before any site is saved (a fresh install, a demo in the middle of `atrium:demo:reset`) every page answered 500 with `RedirectMap::build(): Argument #1 ($siteId) must be of type int, null given`; now nothing redirects and no 404 is logged until there is a site.
- `docker compose up` stopped at `composer install` asking for ext-ftp, and then for ext-intl: the image now has both, which the backup module's FTP destination and the SEO module need.
- `composer install` in a checkout printed six "does not comply with psr-4" warnings for two test fixtures that stand in for classes of other namespaces; they are left out of the classmap now.

## [0.1.0] - 2026-11-20

### Added
- A public demo ([docs/demo.md](docs/demo.md)): `ATRIUM_DEMO=true` and `php artisan atrium:demo:reset` empty the database, fill it with the demo content, remove the uploaded files and make one administrator, `demo@atrium.test` / `demo`, who edits the content, only looks at administrators, sites and languages, has no API tokens, no module settings and cannot change their own name, e-mail or password; the scheduler resets it every hour (`ATRIUM_DEMO_RESET`). `docker compose -f docker/demo/compose.yaml up --build` runs it in one container with limits, `docker/demo/Dockerfile` builds the image.
- Error tracking (`alveby/atrium-errors`, `atrium:module:install alveby/atrium-errors`), kept in the site's own database: PHP exceptions, queue jobs that failed for good, failed scheduled tasks and, when switched on, JavaScript errors of the site and the admin (a small script the module adds to the pages itself, reported to a rate-limited endpoint). Grouped by class and the first five frames of the app's own code, line numbers and changing values left out. **Site health → Errors**: the list with status buttons, search and filters by site, release, level, source and address; an error's page with its trace and code, the request, what happened before, a chart by hour or by day with the number on every bar, the addresses and releases it happens in, every event; resolve, **resolve in next release** (comes back only in another release), ignore, reopen. An **Errors in 24 hours** dashboard tile. E-mail and Telegram alerts for new errors, errors that came back and spikes, once per reason and ten in ten minutes at most. Secrets and personal data scrubbed before anything is stored (no headers, cookies, body or IP; filtered keys, e-mails, cards checked with Luhn, phones). Sampling, a per-minute cap, writing after the response or through a queue, a fallback log when the database is down, 90 days kept (`atrium:errors:prune`). Drivers: `database`, `sentry` (Sentry, self-hosted Sentry or GlitchTip with only a DSN, no SDK), `log`, and your own through `Atrium\Errors\Contracts\ErrorReporter` (Bugsnag, Rollbar, a webhook). Rights `errors.view` and `errors.settings`; an administrator of some sites sees only their errors. `atrium:errors:test` sends a test error everywhere. Guide in `docs/errors.md`. Labels in 15 languages; the chart's colours measured in all five themes.
- Monitoring (`alveby/atrium-monitoring`, `atrium:module:install alveby/atrium-monitoring`), on the site's own server with no outside service. Server timings of every request (time to the first byte, database queries and their time, cache hits and misses, peak memory, 5xx share) by route, site and language, slow queries kept with their values replaced by `?`; written to a file after the response and to the database once a minute in one transaction, with a sample rate and an early flush through a queue; about 0.15 ms added to a request with 20 queries, checked by `atrium:monitoring:benchmark`. Visitors' Web Vitals (LCP, INP, CLS, TTFB, FCP) from a script under 2 KB sent with `sendBeacon`: no cookies, no IP stored, no query strings, Do Not Track and Global Privacy Control respected, a sample rate, 30 beacons a minute from one address, malformed or oversized beacons refused. Uptime checks of every site's front page and added addresses every minute; an incident after N failures in a row (a setting), e-mail and Telegram alerts (token in the settings or `.env`), hooks `atrium.monitoring.incident.opened` / `.resolved`. **Site health → Speed and uptime**: p50, p75 and p95 by day, week or month from mergeable daily histograms, filters by site, language and device, the slowest routes, queries (each with its own page) and pages, links to the error log of a page, checks and incidents; a **Speed and uptime** dashboard tile; charts told apart without colour (markers, dashes, labels, a table of the numbers), colours measured in every theme. Raw data 7 days, daily aggregates 13 months (`atrium:monitoring:prune`). Right `monitoring.view`. Guide in `docs/monitoring.md`. Labels in 15 languages.
- Custom fields (`alveby/atrium-custom-fields`, `atrium:module:install alveby/atrium-custom-fields`): editors add fields to any module from a **Fields** button on its list, with no migration: line, text, integer, decimal, yes/no, date, list, multiple choice, link to a record, file and image, with a name and hint per content language, a tab of the module's form, and the flags required, show in the list, filterable, sortable, searchable, translatable and per site (or shown on one site only). Values live in a JSON column `custom` added with the first field; the filterable and sortable ones are also kept in a typed index table (`custom_field_index`), updated on every save and delete and rebuilt by `atrium:custom-fields:reindex`. `whereCustom()`, `whereCustomBetween()`, `whereCustomFilters()` and `orderByCustom()` on every Eloquent query, and `CustomFacets::for(Product::class, $query)->filters($filters)->counts([...])` / `->ranges([...])` for a filter panel (each field counted with every filter but its own). `atrium:custom-fields:promote` moves a hot field into a real indexed column of the module's table. The fields are in the API (`filter[code]=`, `sort=`, `search=`), its documentation and the MCP tool `describe_module`. On 100 000 records a filtered page of 24 takes 54–185 ms and its three facets 76–374 ms (SQLite, PostgreSQL 17, MySQL 8.4). With `atrium:install --demo` the catalog's products get five filterable fields (weight, battery life, waterproof, connectivity, warranty), named in all 15 languages and weighed in pounds for an English (US) shop, in kilograms elsewhere. Guide in `docs/custom-fields.md`. Admin labels in 15 languages.

### Changed
- The packages no longer require each other in a circle: `alveby/atrium-theme` is below the modules (it names their classes in strings and asks for them only when installed, and no longer lists them in `require-dev`), and the tests that run the skins on the real modules moved to `alveby/atrium-solutions`. `bin/ci` fails its lint step, and a test of the repository fails, when any packages require each other, so a package can be installed and tested alone.
- The panel's sign-in e-mail code (`ATRIUM_2FA_ENABLED`) moved into `alveby/atrium-2fa`, behind the same contract as the other factors. ### Security
- API tokens and MCP keep to the sites their administrator may work with, as the panel does: records of other sites are not listed, read, changed or deleted, `?site=` naming another site answers 404, and new records go to an allowed site. Neither the API nor the panel takes `site_id` from the request any more, so a record cannot be moved to another site.
- Uploads are judged by what the file contains, not by the name the client sends: a script, a page or any other file whose content does not match its extension is refused, and an SVG that can run code (scripts, event handlers, `javascript:` links, embedded HTML, entities) is refused too.
